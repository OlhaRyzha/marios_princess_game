# Аналіз проєкту перед рефакторингом

Дата аналізу: 6 вересня 2026 року
Гілка: `docs/refactoring-plan-2026`
Базовий commit: `43f3799`

## Мета

Зробити проєкт зрозумілим для новачка, відтворюваним на іншому комп'ютері та зручним для безпечного розвитку. Перший пріоритет — середовище й тести. Після цього можна змінювати архітектуру гри, спираючись на перевірену поведінку.

## Поточний стан

Проєкт — Pygame-гра з 37 Python-файлів і приблизно 4 200 рядків коду. Код уже частково розділений на `core`, `data`, `systems`, `ui` та `utils`, але межі відповідальності нечіткі: ігрова логіка, Pygame, файлові ресурси, час, випадковість і переходи між екранами часто зв'язані напряму.

Автоматичних тестів у репозиторії немає. `pytest` випадково присутній у локальній `.venv`, але його немає в `requirements.txt`. Це означає, що новий розробник після встановлення задекларованих залежностей не отримає тестове середовище.

Перевірки поточного стану:

- `ruff check game main.py` — проходить;
- `ruff format --check game main.py` — 12 файлів потребують форматування;
- `pytest --collect-only` — тестів не знайдено;
- headless smoke-перевірка головного меню — один кадр запускається;
- headless перевірка паузи — виявила дві функціональні помилки.

## Середовище та конфігурація

### Що заплутує зараз

`requirements.txt` змішує runtime-залежність (`pygame`) з інструментами розробника (`black`, `flake8`, `ruff` та їх транзитивні пакети). Файл виглядає як результат `pip freeze`, тому з нього незрозуміло, що проєкту справді потрібно, а що підтягнулося автоматично.

Версія Python не зафіксована в репозиторії. Локальна `.venv` створена на Python 3.13.3, а системний Python уже 3.14.4. Інша машина може отримати іншу поведінку або несумісні залежності.

Параметр `SDL_AUDIODRIVER=coreaudio` встановлюється у двох неочікуваних місцях: у `main.py` і навіть у `.pylintrc`. `coreaudio` є macOS-специфічним значенням, тому така конфігурація не повинна бути частиною lint-конфігу й не повинна безумовно застосовуватися на Windows, Linux або у вебзбірці.

У проєкті фактично немає змінних середовища для бізнес-налаштувань і немає секретів. Тому додавання `.env` лише «для сучасності» створить ще один прихований шар конфігурації. `.env` варто вводити лише для параметрів запуску, яким справді потрібні різні значення між середовищами. Безпечні приклади: `SDL_VIDEODRIVER=dummy` і `SDL_AUDIODRIVER=dummy` у headless-тестах.

Шляхи до ресурсів задані двома способами: частина будується від `BASE_DIR`, а частина є відносними рядками на кшталт `assets/audio/level_theme.mp3`. Через це запуск залежить від поточної директорії термінала.

### Рекомендована модель

Єдине джерело правди — `pyproject.toml`:

- підтримувана версія Python;
- runtime-залежності;
- окрема група `dev` для pytest і Ruff;
- налаштування Ruff і pytest;
- команди запуску та тестова конфігурація.

Для початківця найпростіший відтворюваний сценарій — `uv sync`, `uv run python main.py`, `uv run pytest`. `uv.lock` треба зберігати в Git. Це відповідає актуальній моделі uv: `pyproject.toml` описує прямі залежності, а lock-файл фіксує точні версії для всіх машин.

Якщо сумісність з `pip` або itch.io потребує `requirements.txt`, його слід генерувати з lock-файлу, а не редагувати паралельно вручну.

## Тести

### Основна проблема

Тестів немає, а значна частина логіки залежить від глобального стану Pygame:

- `pygame.time.get_ticks()` використовується безпосередньо в персонажі, босах, ефектах, бойовій системі та UI;
- `pygame.key.get_pressed()` читається всередині сцени;
- глобальний `random` використовується при створенні перешкод і ефектів;
- зображення, шрифти, аудіо й display ініціалізуються під час створення великих об'єктів;
- помилки ресурсів та аудіо часто приховуються через широкий `except Exception`.

Такі залежності ускладнюють прості й детерміновані unit-тести. Якщо кожен тест буде самостійно мокати Pygame, тестовий код швидко стане складнішим за ігровий.

### Проста структура тестів

```text
tests/
├── conftest.py               # лише спільний headless Pygame setup
├── factories/
│   ├── __init__.py
│   ├── actors.py             # прості фабрики player/boss
│   └── runtime.py            # стан гри та залежності кадру
├── unit/
│   ├── test_animation.py
│   ├── test_collision.py
│   ├── test_progress.py
│   ├── test_obstacle_factory.py
│   └── test_combat.py
└── integration/
    ├── test_runtime_transitions.py
    └── test_game_smoke.py
```

Правило поділу:

- fixture керує ресурсом або життєвим циклом: Pygame init/quit, dummy display, clock, тимчасова директорія;
- factory створює варіанти тестових даних або об'єктів: player з заданим health, boss у заданій позиції, game state у конкретному режимі;
- test містить лише сценарій Arrange → Act → Assert і перевіряє одну поведінку;
- `conftest.py` не перетворюється на склад зі всіма допоміжними функціями;
- автозастосовувані fixtures використовуються лише для обов'язкової ізоляції Pygame, а не для прихованої підготовки бізнес-даних.

Фабрики мають бути звичайними функціями або fixtures, що повертають функцію. Окрема бібліотека фабрик для такого розміру проєкту не потрібна.

## Архітектура та принципи програмування

### Надмірна відповідальність

`game/app.py::run_frame` займає 184 рядки й одночасно:

- обчислює час кадру;
- читає події Pygame;
- перемикає режими;
- створює сцени;
- оновлює прогрес;
- оновлює та малює активний екран;
- керує web-аудіо;
- викликає display flip.

Це порушує принцип єдиної відповідальності й робить переходи між станами важкими для тестування. Режими зберігаються як довільні рядки, тому помилка в назві виявиться лише під час виконання.

`DemoScene` також є великим координатором: завантажує рівень, керує музикою, collectibles, босом, фіналом, зіткненнями, update і draw. Його слід розділяти поступово, лише після появи characterization-тестів.

### Дублювання

Mask collision реалізований у `game/core/collision.py`, але `CombatSystem` має власну майже таку саму реалізацію. Це створює дві точки для виправлення одного правила.

Шляхи до ресурсів і fallback-логіка розкидані по `data`, `core`, `ui` та `utils`. Централізований `AssetCatalog` або невеликий resolver дасть одну політику пошуку й одну зрозумілу помилку.

### Типи та модель даних

`GameState` — змінний `TypedDict`, режим — `str`, а дані босів — необмежені `dict`. Для ключових доменних понять краще використовувати:

- `Enum` або `StrEnum` для режимів;
- `dataclass` для стану гри й опису боса;
- незмінні колекції для статичних конфігурацій;
- конкретні колекційні типи (`Sequence`, `Mapping`) на межах API.

Це не означає створення класу для кожного словника. Тип вводиться там, де він прибирає реальний неявний контракт.

### Приховані помилки

Широкі `except Exception: pass` приховують причину проблем з аудіо, шрифтами та зображеннями. Для очікуваної деградації потрібні вузькі винятки та зрозумілий warning; несподівані помилки не слід маскувати.

Headless-перевірка виявила:

1. У режимі `menu_pause` викликається `scene.update(0.0)`, але фізика персонажа ігнорує `dt` для гравітації та позиції. Персонаж рухається, поки гра нібито на паузі.
2. Обробник паузи очікує пункт `Продовжити гру`, але `MENU_ITEMS` його не містить. Повернутися з меню можна клавішею Escape, але кнопка, для якої вже написана логіка, недоступна.

Ці дефекти є добрими першими regression-тестами.

## Пріоритети

1. Зафіксувати відтворюване середовище й одну систему інструментів.
2. Створити простий headless test harness і тести поточної поведінки.
3. Виправити підтверджені дефекти паузи.
4. Винести переходи та прогрес у чисту доменну логіку.
5. Зробити час, input і random явними залежностями.
6. Поступово розділити `run_frame` і `DemoScene`.
7. Централізувати роботу з ресурсами й помилками.
8. Лише після стабілізації виконати ширше форматування та очищення застарілих конфігів.

## Що не варто робити на старті

- Переписувати всю гру одночасно.
- Додавати DI-фреймворк, складну шарову архітектуру або фабричну бібліотеку.
- Покривати тестами малювання кожного пікселя.
- Тестувати приватну реалізацію замість поведінки.
- Створювати `.env` з усіма ігровими константами.
- Залишати кілька інструментів з однаковою відповідальністю. У прийнятій конфігурації Ruff відповідає за lint та імпорти, Black — лише за форматування, а Flake8/Pylint видаляються.

Рефакторинг має навчати основних принципів на конкретних прикладах: SRP через розділення циклу гри, dependency inversion через clock/input/RNG, DRY через єдину collision-функцію, explicit contracts через типи та композицію через невеликі системи.
